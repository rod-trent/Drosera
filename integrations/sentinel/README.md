# Drosera for Microsoft Sentinel

Send Drosera's verdicts and canary hits to Microsoft Sentinel, and get analytics
rules, a workbook, hunting queries and two playbooks to go with them.

Nothing here changes what Drosera does. The honeypot still detects and delays,
and never reaches back into anything. This pack only moves the evidence to where
a SOC already works.

```
 Drosera ──[sinks.azure_monitor]──▶ Logs Ingestion API ──▶ DCR ──▶ DroseraEvents_CL
 (stdlib HTTPS, batched, gzipped)                                        │
                                   ┌─────────────────┬──────────────────┼──────────────────┐
                                   ▼                 ▼                  ▼                  ▼
                           analytics rules       workbook        hunting queries   Defender XDR
                                   │                                                advanced hunting
                                   ▼
                              incidents ──▶ playbooks: enrich with honeypot history,
                                                       submit IP to Defender for Endpoint
```

| Piece | File | What it gives you |
| --- | --- | --- |
| Ingestion | [`deploy/ingestion.json`](deploy/ingestion.json) | `DroseraEvents_CL` table, data collection endpoint and rule, sender role assignment, `DroseraSessions` and `DroseraCanaryHits` functions |
| Analytics rules | [`deploy/analytics-rules.json`](deploy/analytics-rules.json) | Five scheduled rules (below) |
| Workbook | [`deploy/workbook.json`](deploy/workbook.json) | Dashboard: KPIs, verdict timeline, top signals, sessions by evidence strength, agent user agents, canary hits |
| Enrichment playbook | [`playbooks/Drosera-Enrich-Incident`](playbooks/Drosera-Enrich-Incident/azuredeploy.json) | Comments any incident's IP entities with their Drosera history, whatever rule raised it |
| Defender playbook | [`playbooks/Drosera-MDE-Indicator`](playbooks/Drosera-MDE-Indicator/azuredeploy.json) | Submits incident IPs to Defender for Endpoint as custom indicators (Audit by default) |
| KQL | [`kql/`](kql/) | Every query above as plain `.kql`, plus hunting queries |

The JSON templates are generated by [`_build.py`](_build.py) from the KQL files and
from the sink's column list in `src/drosera/telemetry/azure.py`. CI fails if they
drift. Edit the sources, then run `python integrations/sentinel/_build.py`.

## 1. Create the table and ingestion pipeline

You need a Log Analytics workspace with Sentinel enabled, and rights to create
resources and role assignments in its resource group.

[![Deploy to Azure](https://aka.ms/deploytoazurebutton)](https://portal.azure.com/#create/Microsoft.Template/uri/https%3A%2F%2Fraw.githubusercontent.com%2Frod-trent%2FDrosera%2Fmain%2Fintegrations%2Fsentinel%2Fdeploy%2Fingestion.json)

Or with the Azure CLI. First decide which identity will send events.

**On Azure compute** (VM, AKS, App Service, Container Apps): use its managed
identity. Its object ID is on the resource's *Identity* blade.

**Anywhere else**: create an app registration:

```bash
az ad app create --display-name drosera-sender --query appId -o tsv
```

```bash
az ad sp create --id <appId> --query id -o tsv
```

```bash
az ad app credential reset --id <appId> --display-name drosera --years 1
```

The second command prints the service principal's object ID, which is the
`principalId` below. The third prints the client secret. Store the secret
somewhere safe; you will not see it again.

Then deploy into the workspace's resource group:

```bash
az deployment group create -g <resource-group> -n drosera-ingestion --template-file integrations/sentinel/deploy/ingestion.json --parameters workspaceName=<workspace> principalId=<object-id>
```

```bash
az deployment group show -g <resource-group> -n drosera-ingestion --query properties.outputs
```

The outputs are the three values Drosera needs: `endpoint`, `rule_id` and `stream`.

> The data collection endpoint and rule must be in the workspace's region. The
> template defaults to the resource group's region; pass `location=<region>` if
> they differ. Role assignments can take a few minutes to apply. A `403` in the
> first minutes after deployment is usually that delay.

## 2. Point Drosera at it

```toml
# drosera.toml
[sinks.azure_monitor]
endpoint    = "https://drosera-dce-xxxx.eastus-1.ingest.monitor.azure.com"
rule_id     = "dcr-0123456789abcdef0123456789abcdef"
stream      = "Custom-DroseraEvents"
min_verdict = "automation"        # human and unknown traffic stays home
# sensor    = "hp-edge-01"        # defaults to the hostname
# auth      = "managed_identity"  # on Azure compute; default is client_secret
```

Keep the credentials out of the file:

```bash
export AZURE_TENANT_ID=<tenant-id> AZURE_CLIENT_ID=<appId> AZURE_CLIENT_SECRET=<secret>
```

A container can skip the file entirely: setting `DROSERA_AZURE_ENDPOINT`,
`DROSERA_AZURE_RULE_ID` (and optionally `DROSERA_AZURE_STREAM`,
`DROSERA_AZURE_AUTH`, `DROSERA_SENSOR`) turns the sink on.

Check it, then backfill anything you have already captured:

```bash
drosera doctor
```

```bash
drosera ship /var/log/drosera/events.jsonl --since 168
```

Canary hits reach Sentinel when the watcher is started with `--emit`:

```bash
drosera canary watch --emit
```

Within a few minutes (first ingestion into a new table can take up to 15):

```kql
DroseraSessions
| where Verdict in ("agent", "hostile_agent")
| order by LastSeen desc
```

### What the sink does and doesn't do

- **It never blocks serving.** Events go into a bounded queue. A background
  thread ships batches every few seconds, gzipped, under the API's 1 MB call limit.
- **It drops rather than backs up.** If Azure is unreachable, events are dropped
  with a warning on stderr. Keep the JSONL sink on as the durable record;
  `drosera ship` can backfill from it.
- **It filters before you pay.** `min_verdict = "automation"` (the default)
  means the ordinary human page views seen by the middleware never leave the
  host. Use `"agent"` to ship only LLM-agent evidence, or `"human"` to ship
  everything. Canary events always ship.
- **It respects `redact_ip`.** Addresses are hashed before any sink sees them.
  That also means IP entity mapping and the sign-in correlation rule have
  nothing to match. `drosera doctor` warns about the combination.

## 3. Analytics rules

```bash
az deployment group create -g <resource-group> --template-file integrations/sentinel/deploy/analytics-rules.json --parameters workspace=<workspace>
```

| Rule | Severity | Fires when |
| --- | --- | --- |
| LLM agent confirmed by comprehension evidence | Medium | A client returned the signed ticket, sent the purpose header, or followed the prose instruction |
| Hostile LLM agent | High | An LLM agent also probed for secrets, admin paths, traversal or injection |
| Canary credential used | High | A planted credential was presented or found. This is proof, not inference |
| Canary file modified or read | Medium | A planted file changed. This is a hint: backups and indexers touch files too |
| Honeypot agent address signing in to Entra ID | Medium, High on success | An address that behaved as an agent on the honeypot is signing in to Entra ID |

The last rule needs the Microsoft Entra ID connector (`SigninLogs`) and is off
unless you pass `deploySigninCorrelation=true`. Deploy the rules only after
events have arrived, because rule validation fails against a table with no
schema yet.

Every rule maps the address to an **IP** entity and the sensor to a **Host**
entity. It also carries the evidence (signals, confidence, user agent) as custom
details, so it can be read without opening Log Analytics.

## 4. Workbook

```bash
az deployment group create -g <resource-group> --template-file integrations/sentinel/deploy/workbook.json --parameters workspaceName=<workspace>
```

It appears under **Sentinel → Workbooks → My workbooks** as *Drosera honeypot*,
with time-range and sensor filters.

## 5. Playbooks

Both playbooks use an incident trigger and a system-assigned managed identity.
They need no stored secrets.

### Drosera-Enrich-Incident

Looks up every IP entity on an incident in `DroseraEvents_CL` and adds a comment
with its honeypot history: verdict, evidence class, sessions, signals, user
agents, first and last seen. Attach it to *all* incidents, not only Drosera's.
A phishing or sign-in incident whose IP already bit the honeypot is exactly
what you want to know about.

```bash
az deployment group create -g <resource-group> --template-file integrations/sentinel/playbooks/Drosera-Enrich-Incident/azuredeploy.json --parameters WorkspaceId=<workspace-guid>
```

Grant its identity (the `principalId` output) read access to the workspace and
responder rights on incidents:

```bash
az role assignment create --assignee-object-id <principalId> --assignee-principal-type ServicePrincipal --role "Log Analytics Reader" --scope <workspace-resource-id>
```

```bash
az role assignment create --assignee-object-id <principalId> --assignee-principal-type ServicePrincipal --role "Microsoft Sentinel Responder" --scope /subscriptions/<sub>/resourceGroups/<resource-group>
```

### Drosera-MDE-Indicator

Submits each IP entity to Microsoft Defender for Endpoint as a custom indicator
and comments on the incident with what Defender accepted.

**Read this before changing the action from `Audit`.** Defender applies network
indicators to connections *from your managed devices*. An indicator will not
stop the agent reaching your honeypot or your website; that is a job for a WAF
or firewall. In `Audit` mode, what it does is raise a Defender alert if any of
your devices ever contacts the same infrastructure. That is the correlation a
honeypot exists for. `Block` stops your devices connecting to the address,
which is rarely what you want for a crawler's cloud IP that other tenants share.

```bash
az deployment group create -g <resource-group> --template-file integrations/sentinel/playbooks/Drosera-MDE-Indicator/azuredeploy.json --parameters IndicatorAction=Audit ExpirationDays=30
```

Its identity needs the Defender for Endpoint `Ti.ReadWrite.All` application
permission (Microsoft Graph PowerShell, as a Global or Privileged Role
Administrator):

```powershell
Connect-MgGraph -Scopes "AppRoleAssignment.ReadWrite.All","Application.Read.All"
$mi   = Get-MgServicePrincipal -Filter "displayName eq 'Drosera-MDE-Indicator'"
$mde  = Get-MgServicePrincipal -Filter "appId eq 'fc780465-2017-40d4-a0c5-307022471b92'"
$role = $mde.AppRoles | Where-Object { $_.Value -eq 'Ti.ReadWrite.All' }
New-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $mi.Id -PrincipalId $mi.Id -ResourceId $mde.Id -AppRoleId $role.Id
```

Plus **Microsoft Sentinel Responder** on the resource group, as above.

### Running them

1. Under **Sentinel → Settings → Settings → Playbook permissions**, give
   Sentinel permission to run playbooks in their resource group.
2. Create an **automation rule**. Enrichment should run when any incident is
   created. The Defender playbook should run when an incident is created whose
   analytics rule name starts with `Drosera -`, and probably only for the
   *Hostile LLM agent* and *Canary credential used* rules.

Prefer running the Defender playbook manually from an incident until you trust
the verdicts on your traffic. `drosera report -f mde` produces the same
indicators as a CSV for Defender's bulk import, for review first.

## 6. Hunting and Defender XDR

[`kql/hunting/`](kql/hunting/) holds queries that join Drosera with the rest of
your telemetry:

- **defender-device-contact.kql**: managed devices that connected to, or
  accepted connections from, addresses that behaved as agents on the honeypot.
  Needs `DeviceNetworkEvents` from the Defender XDR connector.
- **production-web-traffic.kql**: the same addresses in Front Door or
  Application Gateway logs. Is the agent that explored the honeypot also
  exploring production?
- **new-agent-user-agents.kql**: agent user agents first seen today against a
  30-day baseline.

If the workspace is onboarded to the **unified Defender portal**,
`DroseraEvents_CL` and both functions are queryable in Defender XDR *advanced
hunting* next to the `Device*` tables. Any of these queries can become a
Defender **custom detection rule** there. That route suits you if your SOC
works in the Defender portal rather than Sentinel's.

## Cost

Ingestion is billed per GB into the Analytics tier. A rough guide is 1 to 2 KB
per shipped event. A standalone honeypot sees almost only non-human traffic, so
nearly everything ships. Behind the middleware, `min_verdict` is what keeps
cost proportional to the evidence rather than to your traffic. Set the table's
retention separately from the workspace's if you want to keep honeypot evidence
longer (or shorter) than the rest.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `HTTP 403` from the sink | Role assignment not yet applied (wait ~10 min), or assigned to the wrong object ID. It must be the *service principal's* object ID, not the app ID |
| `HTTP 404` | `rule_id` must be the DCR's **immutable ID** (`dcr-…`), not its name or resource ID; `stream` must be `Custom-DroseraEvents` |
| `token request failed` | Wrong tenant, client ID or secret, or an expired secret |
| Nothing arrives, no errors | Everything is below `min_verdict`. Run `drosera report` locally to see what the sink is filtering |
| Rules fail to deploy | Deployed before `DroseraEvents_CL` had data, or the sign-in rule without `SigninLogs` |
